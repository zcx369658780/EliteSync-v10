## 1. 记录族和严格形状

拟新增独立 family 常量 `MESSAGING_CONSENT_STATE_TRANSITION_DERIVED_PROJECTION`。它不能复用 `PRODUCT_CONNECTION_STATE_TRANSITION_DERIVED_PROJECTION`：BA-05 把 CN 与 MC 的 aggregate、来源、修订和用途分开，现有 Product Connection family 的 typed payload 与状态规则也只接受 CN。该新名称是**本候选的合同提案**，仅在 Work 接受后才可用于后继代码任务。

记录沿用现有逻辑 repository 的顶层 envelope，**恰好**包含 `logical_record_identity`、`record_family`、`bindings`、`source_revision`、`source_condition`、`currentness`、`freshness`、`logical_intent`、`authoritative_outcome`、`authoritative_outcome_metadata`、`correction_metadata`、`projection_metadata`、`transport_observation`、`private_fixture_extensions`、`derived_projection_payload`；拒绝额外键。`private_fixture_extensions` 必须为空；不存消息正文、账户信息、真实身份、Token、密码、Safety 材料或历史 Conversation 内容。`record_family` 固定为上述 MC family。`bindings` 采用现有 Common Authority 十一个命名字段（owner、scope、actor、actor_role、subject、participants、audience、purpose、aggregate_context、lifecycle_identity、terminal），逐字段严格比较，键插入顺序不作为 authority；这里的 owner/actor 固定为 **MC_DERIVATION** 而非 MC 源 writer，subject 固定当前 Connection identity，aggregate/lifecycle context 固定当前 consent identity，audience 固定内部开发态持久化，purpose 仅为 `CONVERSATION_LIVE_READ` 或 `CONVERSATION_LIVE_SEND`。不同 purpose 不能共用一条 MC 记录或一个 revision 流。

`derived_projection_payload` 有且仅有以下共同键：`schema_marker`、`payload_kind`、`consent_identity`、`connection_identity`、`participant_references`、`requester`、`recipient`、`purpose`、`classification`、`current_state`、`proposed_state`、`reason_categories`、`connection_dependency`、`consent_state_dependency`、`transition_dependency`、`terminality`、`invalidation`。`schema_marker` 分别为 `mc-current-derived-v1` 或 `mc-transition-derived-v1`；`payload_kind` 分别为 `MC_CURRENT_STATE` 或 `MC_TRANSITION`。当前态记录的 `classification` 只能是六个 MC 状态之一或 `UNKNOWN`，`proposed_state` 和 `transition_dependency` 必须为 `null`；转移记录的 `classification` 只能是 `ADMISSIBLE/REJECTED/UNKNOWN`，`current_state` 与 `proposed_state` 为六态或 `null`。`reason_categories` 是有界、去重、按固定次序的非私密枚举，不收原始异常或证据正文。`terminality` 仅包含 `current_state_terminal`、`proposed_state_terminal`、`terminal_reopen_rejected` 三个布尔值；当前态无 proposed state 时相应值为 `false`。`invalidation` 仅包含 `invalidated` 布尔值、`relation`、`dependency_identity`、`lifecycle_reset=false`、`consent_reopened=false`；无失效时两个可空字段为 `null`。额外键、错误类型或未知 schema marker 一律拒绝存储。

三个 dependency 槽仅容纳**来源证据的脱敏固定投影**，不是新权威证据；结构如下。`connection_dependency` 和 `consent_state_dependency` 各有且仅有 `evidence_identity`、`authority_owner`、`authority_scope`、`subject`、`participant_references`、`audience`、`purpose`、`aggregate_context`、`lifecycle_identity`、`state`、`source_lineage`、`source_revision_value`、`source_condition`、`currentness`、`freshness`、`protected_binding_satisfied`。前者的 state 必须是 CN vocabulary，后者必须是 MC vocabulary；两者独立的来源 owner/scope/lineage 不互相覆盖。`transition_dependency` 在同样来源绑定字段外，恰增加 `transition_identity`、`actor`、`from_state`、`to_state`、`expected_state_revision`；`expected_state_revision` 必须是 MC 当前态来源的完整 owner/scope/lineage/context/value 五元组，不能用 CN revision 或全局序号替代。对应证据缺失时槽位为 `null`，分类只能为不可用的 `UNKNOWN`；严禁用空对象伪造“存在”。两个参与者必须恰为两个不同、非空、同一当前 Connection 的引用；requester 与 recipient 是其中不同的人，固定于 consent identity，不能在同一身份下交换。source binding 的 subject、participant、purpose、aggregate/lifecycle context 必须与记录逐字段相符。

顶层 `source_revision` 明确标为 **MC_DERIVATION 的关联修订**：owner/scope 为此 family 与 payload kind，lineage 为 `(consent_identity, purpose, payload_kind, MC 来源 lineage)` 的稳定规范化摘要，value 仅映射该 MC 来源本地修订；它不是 CN 修订、跨 MC 全局修订或 MC writer 的凭据。`source_condition/currentness/freshness` 是本条派生记录对所有必需来源依赖的保守聚合：任一 false 则 false，任一 unknown 且无 false 则 null；不能因 SQLite 存下记录把 null 变 true。`projection_metadata` 固定投影 identity、represented revision、lag、currentness，并永久标记非 authority；`transport_observation` 只描述传输观察，不能决定 domain outcome。`authoritative_outcome` 默认为 `UNKNOWN`、metadata 为 `null`；仅当同一 immutable intent 的精确来源证据明确携带 outcome 且可独立绑定时，才可保留 source-carried metadata。synthetic fixture 中的“committed”只是假定来源回执，不是现实 MC 生效证明。不能由 `STORED_NEW`、投影读回或 timeout 推造 committed。

## 2. 稳定身份、转移和冲突

每个 synthetic 来源断言须提供不可变 `evidence_identity`；转移另提供不可变 `transition_identity`。`logical_intent.intent_identity` 固定为 `(payload_kind, evidence_identity 或 transition_identity)` 的规范化摘要；`logical_record_identity` 固定为 `(family, logical_intent.intent_identity)` 的规范化摘要，**不把可变 payload 内容加入 identity**。`logical_intent.semantic_input` 保存规范化的完整非私密输入快照及依赖摘要。相同 identity、相同 semantic input 和结果只能 `EXACT_DUPLICATE`；相同 identity 改变任何绑定、修订、状态、角色、用途、依赖或结果须 `CHANGED_INPUT_REUSE_REJECTED`，不能生成另一个 id 来绕过。两个来源事件身份碰撞、同一 MC lineage/revision 语义不同须冲突并停；不同 lineage 不可比较，不能按写入时间、到达顺序或 transport 顺序选“当前”。可比较的旧 revision 只保留历史相关性，不得覆盖较新态。

接受的 MC 直接转移仍严格为：`MC_NONE→MC_PENDING`（当前 `CN_ACTIVE` 中任一参与者发起）；`MC_PENDING→MC_ACTIVE/MC_DECLINED`（同一请求绑定的 recipient）；`MC_PENDING→MC_WITHDRAWN`（绑定 requester）；`MC_ACTIVE→MC_REVOKED`（任一绑定参与者）。无 `MC_NONE→MC_ACTIVE`，无 MC pause/resume/close。`MC_DECLINED`、`MC_WITHDRAWN`、`MC_REVOKED` 对**旧 consent identity** 终态；新尝试必须有新的 consent context/request/evidence identity，走新的 `MC_NONE→MC_PENDING`，不从旧终态重开。`MC_REVOKED` 是 MC 来源状态；generic `REVOCATION` invalidation relation 是对记录依赖的失效标记，不能互相替代。来自来源的 correction/supersession/revocation 必须指定旧 dependency/record identity、来源关系与新证据 identity；失效旧投影而不改写旧来源或合成新 MC 状态。若目标不精确、旧记录不存在或新旧来源关系不可比较，读回保持 `UNKNOWN/INVALIDATED/INCOMPARABLE`，不恢复历史 `MC_ACTIVE`。

重复提交只复用同一 immutable intent；超时或传输未知只能按 identity 对账，不能推定成功、失败或直接重发造成第二个意图。乱序到达以同一来源 lineage 的严格 revision 判断；较新 `MC_REVOKED` 使旧 `MC_ACTIVE` 不可作 live gate，较旧 active 后到也不能复活。等 revision 冲突、不可比 lineage、重复 identity 不同内容、跨 Connection/参与者/用途、缺失/过期/不新鲜/`UNKNOWN` 一律不可用于受保护动作。存储可记录脱敏拒绝理由，但**不可用记录的存在不是授权**。

## 3. 与现有接口的最小映射

输入侧为固定 synthetic consent/context、MC 当前态及转移来源证据、独立 CN 当前态来源证据；`MessagingConsentConversationLiveGateEvaluator` 只作派生求值，不产生来源。输出侧分别是 evaluator 的分类/原因/依赖向量、上述 typed record、repository `store/readExact/resolveCurrent/observeInvalidation` 的关联状态，以及 application boundary 的非权限读回。`SqliteInMemoryLogicalPersistenceAdapter` 必须显式承认此新 family 的 typed payload，否则现有允许列表会剥去 payload；内存与 SQLite 两个 adapter 必须对相同输入返回相同接受/冲突/不可比/失效结果。查询键至少含 family、派生 owner/scope、consent aggregate、purpose 与来源 lineage；严格 readback 还核 record/intent identity、完整 bindings、来源修订、typed payload 与失效状态。只以 family+consent identity 读到一条记录不足以判断当前。

派生 live-read 与 live-send 投影必须分开，分别记录其 MC purpose 与独立 CN/MC 依赖；read 的结果不能充当 send，transport 结果不能充当权限。**使用点**须另外获取当前、来源可验证且上下文匹配的 `CN_ACTIVE` 与同用途 `MC_ACTIVE`；send 在消息提交时再次核两输入。任何投影读回、持久化 disposition、离线缓存、历史 Conversation 或较早允许结论均不能替代这一步。真实 MC 来源、writer 和应用层受保护动作的完整接线仍 `NOT_READY`，不由本 synthetic 合同推断。历史 Conversation 读取、消息正文、保留/删除/导出、Safety、真实身份、Token、离线凭据均不在此合同。
