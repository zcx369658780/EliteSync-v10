## 2. 最小持久化候选（**PROPOSED**，非 migration）

**建议先评审独立的成功交互登录事件记录**，而非在 `users` 上覆盖一个裸时间字段。每条事件必须能够说明同一账户、同一已验证设备、服务端确认的成功交互登录、受信发生时间、可比较顺序和来源。下表是验收所需的逻辑字段，不决定 SQL 类型、表名、加密算法或真实设备标识。

| 候选逻辑项 | 目的与约束 | 尚待决定 |
|---|---|---|
| 事件 ID / 幂等键 | 防重试重复写入；同一服务端确认事件只形成一条记录。 | 生成者、唯一键长度/作用域及重试协议。 |
| 账户关联 | 指向经受信认证的 `users` 主体；不可从请求自填 user ID 判权。 | 实际 FK、账号删除后的事件保留/删除及数据权利。 |
| 不含明文设备秘密的绑定引用 | 区分同账户不同设备，离线凭据只绑定对应设备与锚。 | 设备证明、轮换/丢失、更换设备与隐私保护方案。 |
| 服务端确认的事件类别与 `T0` | 只允许成功交互登录写入此类事件；注册、refresh、启动、恢复、Token 轮换不能写入或重锚。`T0` 必须来自受信服务端时间来源。 | 服务端认证边界、时间来源、时区/精度与异常处理。 |
| 同账户/设备可比较的严格递增顺序 | 对并发登录、乱序回执、重放作事务内裁决；唯一性至少应覆盖账户、设备绑定和顺序，幂等键另需唯一。最新锚须按权威顺序选取，不能按客户端到达顺序或 Token 时间排序。 | 序列分配、事务/锁、跨节点与跨设备比较语义。 |
| 来源与状态关联 | 能追溯是哪一个受信登录 authority 确认，且已知登出、撤权、禁用、账号删除后旧事件不可重新开门；敏感证据最小化。 | 来源回执格式、撤权/失效记录及保留政策；不可在日志或普通证据泄露凭据。 |

**候选写入不变量**：同一事务/一致性边界内，只有认证成功且账户未禁用的交互登录才可确认事件与顺序；失败、重复、并发冲突必须不产生可用新锚。refresh 仅轮换 Token，保持原锚。建议以受信事件记录推导当前锚；若为性能另存投影，必须能证明投影与事件一致，不能用投影覆盖冲突或旧撤权。AUTH-09 可作为纯语义反例参考，其声明输入和 `proposed_anchor` 均不能直接写入真实库。

**账号/失效关联**：本地 `AuthController::deleteSelf()` 仅有受限 synthetic 账号删除路径，先删 tokens 再删 user；没有本候选事件表。未来需选择删除、撤销、隔离和审计保留的合法终点及 FK 行为，避免孤儿事件或删除后旧离线凭据复活；本文不擅定 cascade、软删除或保留期。离线远端撤权不可能保证即时传播，已知失效须优先锁定，并在联网时重验。

**旧数据/回退**：既存用户和 Token 没有可信交互登录锚，标记 `UNKNOWN`；不得从 `users.created_at/updated_at`、`sessions.last_activity` 或 `personal_access_tokens.created_at/last_used_at/expires_at` 回填伪 `T0`。后继若上线新机制，缺锚设备须锁定受保护离线内容并通过新的受信交互登录取得锚；旧客户端和 API 在兼容窗内如何拒绝误授权须另评审。回退首先关闭新授权路径并保持私密内容锁定；结构回滚、事件保留及账号恢复必须依迁移前已验证的备份和明确数据权利决定，不用 destructive down migration 代替恢复计划。
