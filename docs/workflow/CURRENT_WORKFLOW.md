# EliteSync-v10 当前工作方式

2. Codex 是本项目指定会话的版本实现负责人。版前 Astra 给目标草稿，Codex依据真实代码与环境反馈目标和执行建议；集中解决实质分歧，再确立正式版本。迁移后首版尚未制定，等待 Owner 手动启动第三阶段。
3. 正式版本冻结目标、范围、验收标准、关键科学/产品契约和已接受限制，登记冻结提交。Astra、Work、Codex均不得因执行不理想追改本版计划。路线图仅为未来版本更新。计划错误保留原件，必要时结束本版、另立后续版本。
4. 范围内的实现顺序、内部拆解、相关代码/测试、普通调试及修复由Codex自主调整。失败优先进入诊断、修复、重测循环；不用逐步骤批准或反复请求继续。保留有效测试、原始失败和实际验证，不为绿色结果降低标准。
5. 真正缺必要决定、越权、未授权不可逆操作或持续无进展/额度与环境阻碍时，保存状态并报告。会话交接续接原版本，不重新立项。旧暂停任务不因本迁移恢复；旧冻结预算和拒绝原件不复活。
6. 完成后集中提交候选代码身份、实际验证证据和剩余问题。Astra对照原冻结标准读取真实实现，批量反馈原目标内缺陷；修复续接同版，新需求/纯优化进入后续版。Codex自测通过不等于最终验收，开发验收不等于生产发布。
7. 每版通过、部分完成、失败或终止都记录原因与证据，区分执行偏差、计划遗漏/错误、环境阻碍、验证不足、验收漂移。未来试运行顺手记录目标完成情况、集中返修轮数、人工干预/流程阻塞、实际可取得的用时和额度；未知写UNKNOWN，不建立自动监控，不把经验自动变成永久门禁。
8. GitHub用于版本文件交换、证据发布及备份，不是微步骤审批总线。无顾问自动轮询、自动插单、实时监督、后台监听或自动调度。GitHub备份不代替生产数据、凭据及真实资产保护。
