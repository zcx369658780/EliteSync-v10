# EliteSync-v10 当前工作方式

**2026-10-21前瞻补充：** 当前短状态唯一入口 [ACTIVE_STATE](ACTIVE_STATE.md)；独立功能验收由Astra直接归档，集成不重复功能重测；项目源按里程碑增量同步。完整生效规则见 [轻量验收与项目源同步](ACCEPTANCE_INTEGRATION_SOURCE_SYNC_20261021.md)。原冻结AC/Owner及系统权限门禁均不变。

生效依据：2026-10-12角色迁移、2026-10-13版后接续授权，以及2026-10-14 Owner批准“APP前后端与数据库恢复＋独立Web管理面板”的路线调整。本文是项目工作约定，不替代工具、账户权限或具体实施授权。

## 1. 角色与版本单位

Owner决定方向、真实产品取舍和重大不可逆事项。Astra负责长期路线、版本目标、最终独立验收和复盘；Codex负责已派发版本的调查、实现、调试、测试与集中交付。旧Work/dot实时监督、日常微步骤审批和强制新增多模型审查链不恢复。

以[当前路线图](../architecture/ELITESYNC_V10_CURRENT_DELIVERY_PLAN_AND_ROADMAP_V0_1.md)和[恢复功能台账](../architecture/RESTORATION_CAPABILITY_MATRIX.md)组织功能版本。冻结的是可观察功能结果、相关模块、环境与数据范围、验收标准，不再默认“一页/一个源码文件就是一版”。为同一冻结功能所需的前端、后端、数据库、管理UI和测试可成组实施；具体受保护排除项仍明确，不为多改一个相关文件就另开版本。

## 2. 从计划到真实交付

Astra给版本目标，Codex对本版必要源码/可用备份/环境集中反馈，解决真正缺少的决定后冻结；Owner手动派发，Codex范围内自主推进。恢复来源的具名核查在功能版本内部为实现服务，不先发连续只读考古或全仓环境治理版本。普通失败进入修复重测；缺来源、冲突或权限只暂停相应风险部分并集中报告。交接续接原目标，不重新立项。

后续恢复版本的最终验收是“APP/Web管理端→实际业务后端→独立持久化数据库→重新读取/重启后正确结果”。可使用开发账号、虚构/脱敏数据，不可以两端独立mock或静态投影代替贯通。单元/Widget测试仍用于回归，不能冒称完整软件恢复。未恢复的具名功能、缺备份与数据范围必须明示，是否削减由Owner决定。

保留不可变冻结计划、原有效测试和原始失败；每版集中交付固定候选、必要代码/测试、实际运行和少量安全证据。Astra按冻结目标独立裁决、一次集中返修原范围缺陷。退出码与stdout同时核对，分析exit0不等于无lint。不统计文档/断言/提交数充当产品完成率。

## 3. 恢复来源与开发环境

Owner已批准以旧APP有效资产为恢复来源，旧“不得逐项恢复9.x/不得读取任何旧项目”的方向性限制不再是恢复任务的默认障碍。仅在具名恢复任务里读取已确认归属的历史源码、现有v10 LOCAL_ONLY及备份副本；不无限扫描会话/其它项目，不因旧资产存在就覆盖新实现或自动接受。备份原件、原脏主树和未提交独立成果保留。

正式实施计划应一次明确开发服务/端口、独立数据库、数据或具名备份副本范围、构建目标和测试设备。派发后在这些范围内启动后端、迁移或写入开发库、运行必要任务、开发账号读写、编译安装及跨端测试属于授权恢复工作，不逐命令再请求批准。普通工具/依赖问题按实际环境处理；需要新增下载、升级、费用、账户访问或系统级变更而原计划未涵盖时，集中提出该项需要，不无限扩成环境审计。

生产数据库覆盖、真实数据用途变更或外传、原始备份删除、密钥公开、真实第三方付费/账号操作及不可逆资产处理仍需具体授权。管理权限必须在后端落实，不只隐藏按钮；消息恢复须证明合法账号可用、越权拒绝，不以永久404代替功能，也不全局移除鉴权。

本轮路线文档及同步不启动数据库/服务/构建，不修改BE-12运行代码。旧V57/H1/H2/D0任务本身仍停止，不追认其历史运行；新恢复版本按当前目标一次明确具体开发权限，不要求先重走旧治理链。NOT_READY/RuntimeReady/M6旧标签不是新开发版的全部禁止令，也不是已获生产资格。

## 4. 验收后集成与本地接续（K08前瞻简化）

Owner已批准每版独立接受后默认接续安全集成、本地可用基线及必要回归，再规划下一版；不用反复确认这个顺序，仍由Owner手动把本地任务转给Codex，不运行后台自动派单。

GitHub集成须基于真实main差异、接受范围与固定源码身份，保留历史计划/接受/拒绝和原始候选，不混入无关LOCAL_ONLY或敏感原证。无需以整包历史merge代替必要成果集成；有冲突先保留并集中报告。

后续可继续使用一条专用的干净集成开发基线，无损核对后按授权接续；**不再要求每次收尾都新增完整worktree、重验所有历史树或因纯文档提交重复应用测试**。确有隔离需求才创建新工作树。原dirty root不得盲目pull/reset/rebase/clean/stash；不擅自prune/delete旧树。根据实际触及资产保留保护核对，过去冻结任务的109项/11树等原证不修改，不自动成为未来每版固定数量门。

分别记录Acceptance、GitHub代码集成、本地可用基线、原dirty root是否吸收、目标基线实际运行。是否重跑和测试范围按实际集成差异确定；未运行写NOT_RUN，不能把旧候选通过声称新目标通过。网页未直接读取的Windows原证标CODEX_REPORTED，不创造本机访问或同步事实。

## 8. 长任务单与中途无监督模式（Owner再次明确，2026-10-25）

v10.x默认采用“一份冻结计划、一份综合长任务、一次集中候选与独立验收”。Codex在Owner冻结的版本/功能范围、已授权本地环境和预算内，可自主调查、实现、集成、构建、测试、调试并修复普通失败；不要求每个文件修改、命令、测试失败或范围内返修都单独创建任务或等待Owner放行。目标是尽快完成尚未上线验证的功能模块，而不是用微任务与逐步审批替代开发。

只有方向性决策、超出冻结范围、生产/真实用户数据、敏感外传、真实费用、系统/全局安全设置、供应商/实人操作、不可逆资产或Owner明确保留的风险才暂停请求Owner。真实执行策略拒绝属于环境阻断：如实记录，不伪造结果、不隐瞒、不直接修改策略或规避限制；在既有授权内可使用已批准且合法的方式继续，否则集中报告阻断。

任务单应把成功目标、范围、验收合同、可自主修复/重试事项、总预算、真正的停止条件和最终交付一次写清。Astra在综合交付后集中独立验收，必要时一次性给出修复清单；静态审查不自动成为每个普通测试动作的额外审批门。稀缺的一次性预算/硬时限只有Owner明确设定时才按硬门禁处理，失败后不自动重置。

本节与第7节共同生效：A-D是任务发布的交付闭环，不是运行中逐步骤审批流程；发布后Owner手动派发，Codex在任务范围内中途无监督执行。

正式任务发布统一遵循[A-D Task Dispatch Closure Protocol](TASK_DISPATCH_CLOSURE_PROTOCOL.md)：

- **A 授权与冻结**：核对Owner明确授权、原任务、ACTIVE_STATE、live main/Root、候选HEAD、禁止事项和预算。授权明确即执行，不重复提问；不明确才询问。
- **B 唯一任务单**：创建唯一正式任务文件，取得Blob SHA并立即按路径读回，确认正文、目标、预算与STOP条件一致。没有成功创建和正文读回，不得称任务已发布。
- **C 状态同步与验证**：更新ACTIVE_STATE，再fresh回读live main、Root、任务Blob/正文和状态Blob；必要时核对产品Tree。任何步骤失败，明确报告部分完成状态，不静默结束，不盲目重复创建。
- **D 一次性交付**：同一条回复提供任务链接、Blob SHA、最终回读的main/Root/ACTIVE_STATE Blob、当前状态、停止门禁，以及单一可复制Markdown代码框启动Prompt。Prompt不含开始/结束包装标记、不嵌套代码框。

任务发布不是Codex派发或执行。Owner仍手动派发；Codex只执行正式任务单明确范围。交付后等待Astra独立复核，不自动派发后继、合并产品或越级放行下一Gate。若任务单已创建但状态同步/回读失败，必须使用`TASK_PUBLISHED_STATE_SYNC_INCOMPLETE`或`PUBLISHED_READBACK_UNVERIFIED`等部分完成状态准确报告。

Owner于2026-10-25批准该规则；仅前瞻生效，不追溯改变已冻结任务的权限、预算与验收结果。
