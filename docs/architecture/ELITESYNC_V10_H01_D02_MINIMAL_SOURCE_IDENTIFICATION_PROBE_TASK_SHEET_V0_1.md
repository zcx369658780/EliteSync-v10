## 8. Content-blind candidate resolver

After a permitted locator identity is extracted, only content-blind repository metadata at the accepted revision may resolve it to an exact immutable candidate path/blob. The resolved candidate must not be opened.

Permitted resolver operations are limited to:

- exact accepted-revision tree/path inventory, transiently filtered by the exact locator identity to retain only matching candidate paths;
- exact accepted-revision path-to-blob lookup for a surfaced candidate path;
- exact object type lookup;
- exact object byte-size lookup;
- exact path-scoped no-patch provenance retaining only commit SHA, parent SHA(s), timestamp, subject, path status, modes, and old/new object SHAs.

Locator-to-path matching must be deterministic by locator type:

- an explicit repository-relative reference may match only a path that is exactly equal after separator normalization; no prefix, suffix, basename, substring, or fuzzy match is permitted;
- a namespace-qualified identity may be transformed only by a pre-authorized reversible namespace-to-repository-path mapping stated verbatim in the fresh Stage A authority; the artifact must record the input identity, exact mapping rule, and resulting single lookup path;
- a bare class, interface, trait, method, function, table, model, entity, imported symbol, or used symbol without an explicit repository-relative reference or pre-authorized reversible mapping is unresolved and must not drive basename, substring, directory, naming-convention, adjacency, or repository-wide candidate search;
- a method/function token may not independently resolve a file path unless the same retained locator chain includes an explicit path or namespace-qualified containing identity covered by the deterministic rules above.

Permitted command families may be equivalent only to:

- `git ls-tree -r --full-tree <accepted-revision>` with immediate exact locator filtering and only matching paths retained;
- `git ls-tree <accepted-revision> -- <exact-surfaced-path>`;
- `git cat-file -t <exact-resolved-sha>`;
- `git cat-file -s <exact-resolved-sha>`;
- `git log --all --root --format="%H%x09%P%x09%aI%x09%s" --raw --no-abbrev --no-renames -- <exact-surfaced-path>`, with no patch or body.

Unmatched tree rows must not be displayed, persisted, summarized, classified, searched, or used. Resolver operations must not use `git show`, `git cat-file -p`, `git grep`, `rg`, grep, code/symbol search, AST, indexing, dependency/reference/call traversal, path adjacency, sibling enumeration, schema inspection, tests, builds, runtime, logs, environment access, external search, or source content.

Resolution may produce only:

`PROBE-DISCOVERED PROPOSED EVIDENCE CANDIDATE`

That identity remains inactive and unread. No resolver ambiguity authorizes opening multiple candidates or broadening the probe.

### 8.1 Defensible-identity threshold and ambiguity handling

A class may receive `PROBE IDENTIFIED DEFENSIBLE CANDIDATE IDENTITY` only when every counted identity satisfies all of these conditions:

- the retained locator fact is a bare exact identifier, namespace-qualified identity, or explicit repository-relative reference from an authorized probe;
- the locator fact is recorded without line number, source sentence, surrounding context, or semantic explanation;
- exact accepted-revision metadata resolution produces exactly one repository-relative path and one blob SHA for that locator;
- exact object type and size are established;
- the locator-to-path chain contains no content follow-through, inferred synonym, fuzzy match, ranking, or executor selection;
- minimum necessity and overlap are recorded without correspondence or behavior inference.

If one exact locator produces more than one exact accepted-revision metadata match, retain every exact matching path/blob as a separate deduplicated proposed-candidate identity, do not rank or select among them, assign the affected class `PROBE IDENTIFIED PARTIAL / AMBIGUOUS CANDIDATE SET`, and stop resolution for that locator. Deduplicate only identical repository/revision/path/blob tuples. Do not open candidates or read another source merely to disambiguate unless the progressive next-read rule independently permits the next exact probe for the still-unresolved class.

If a locator produces no exact path/blob match, retain the no-match resolver result and the remaining gap. Do not relax the match, search approximate names, infer a neighboring path, or create a candidate record. Candidate count has no arbitrary numeric target: it equals only the finite set of exact deduplicated matches directly produced by recorded authorized locator facts.
