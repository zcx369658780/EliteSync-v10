## 7. Target-independence test

`STATIC / TRACKED / READ-ONLY != TARGET-INDEPENDENT`.

Every candidate question and finding must separately pass all ten tests:

1. **Direct static visibility:** Is the claim directly visible in one or more exact allowed blobs at the authorized commit?
2. **Target removal:** With accepted-target count still zero, does the claim retain identical wording, scope, and confidence?
3. **No embedded criterion:** Does it avoid implying latency, availability, consistency, recovery, capacity, cost, privacy, Safety, fairness, comprehension, accessibility, audit, retention, deletion/export, pacing, SLA/SLO, staffing, operational, quality, or configuration success criteria?
4. **No alternative selection:** Does it avoid comparing, selecting, recommending, rejecting, optimizing, or preferring alternatives?
5. **Exact closed provenance:** Can a reviewer reproduce it from an exact Section 4 path, authorized commit, locator, mode, and blob/hash without another source?
6. **No unresolved empirical dependency:** Does it remain true without U-05 activity, U-08 evidence, U-10 validation, Safety/legal authority, telemetry, measurement, runtime, production, or external evidence?
7. **No product/operations promise:** Does it avoid a user-facing promise, operational commitment, quality claim, acceptance criterion, design-entry verdict, or readiness claim?
8. **No conceptual-to-technical collapse:** Does it avoid converting Product Truth, Domain, or Information responsibility into a module, service, table, interface, owner, or deployment boundary?
9. **No manufactured authority:** Does it avoid promoting a name, dependency, route, config, import, default, bootstrap label, historical behavior, vendor behavior, sample, comment, or AI judgment into current authority?
10. **No reference expansion:** Is the claim complete without following an import, include, route target, dependency, neighbouring path, generated artifact, or external reference?

Allowed results:

- `PASS — DEMONSTRABLY TARGET-INDEPENDENT STATIC FACT`; or
- `FAIL / UNDEMONSTRATED — CLASSIFY ONLY; DO NOT EXPAND OR DECIDE`.

Any ambiguity or failed test requires `UNKNOWN — NOT ESTABLISHED`, `TARGET-DEPENDENT — BLOCKED`, `OUT OF SCOPE — NOT INSPECTED`, or `CONFLICTING EVIDENCE — STOP FOR REVIEW`. No target, assumption, source expansion, runtime check, or technical judgment may be introduced to make a finding pass.

## 8. Evidence-state and record rules

### 8.1 Primary evidence states

Every finding must use exactly one:

| State | Permitted meaning |
| --- | --- |
| `OBSERVED — STATIC REPOSITORY EVIDENCE` | Directly reproducible literal/structural content in an exact allowed blob; not runtime, acceptance, readiness, or authority. |
| `INFERRED — REQUIRES REVIEW` | A bounded dependency interpretation with cited premises; not an accepted technical fact or decision. |
| `UNKNOWN — NOT ESTABLISHED` | Allowed evidence does not establish the claim; not negative evidence. |
| `OUT OF SCOPE — NOT INSPECTED` | Answering requires an excluded source or activity. |
| `TARGET-DEPENDENT — BLOCKED` | The item depends on a concrete target or target-dependent decision lacking exact-scope authority. |
| `CONFLICTING EVIDENCE — STOP FOR REVIEW` | Allowed static text conflicts with accepted authority or cannot be reconciled without expansion. |

No finding may use `ACCEPTED TARGET`, `REQUIREMENT`, `SELECTED`, `RECOMMENDED`, `APPROVED ARCHITECTURE`, `DESIGN-READY`, `IMPLEMENTATION-READY`, `PRODUCTION-READY`, or equivalent upgraded language.

### 8.2 Required fields for every finding

Each finding must contain:

1. unique ID;
2. exact bounded claim;
3. one primary evidence state;
4. exact path and authorized commit;
5. line/section/symbol locator;
6. file mode, Git blob ID, and SHA-256 unless sensitivity stop applies;
7. static reading method;
8. scope and limitations;
9. all ten target-independence results;
10. quality-family applicability or `NOT DETERMINED — NO SILENT WAIVER`;
11. upstream-authority trace;
12. unresolved U-05/U-08/U-10/U-12/U-14/U-15, Safety, legal, target, or operational dependency;
13. prohibited inference; and
14. affected-item/scope or whole-task stop condition.

### 8.3 Interpretation rules

- Presence proves only static presence at the authorized commit.
- A manifest/lockfile proves only its declarations, not installation, resolution success, support, compatibility, security, or runtime use.
- Configuration proves only literal static configuration expressions, not effective values or deployed state.
- A route/client/repository/storage declaration proves only its static representation, not execution, reachability, persistence, ownership, correctness, or accepted contract.
- A bootstrap/platform declaration proves no canonical architecture or readiness.
