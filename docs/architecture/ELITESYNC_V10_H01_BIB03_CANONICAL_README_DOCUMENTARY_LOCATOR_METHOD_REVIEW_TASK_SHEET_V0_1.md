## 4. Proposed two-stage structure

The proposed method has exactly two later stages.

### CR-1 — canonical README identity resolution

A separately authorized future execution may use one repository-native canonical README resolution mechanism equivalent in semantics to requesting the repository's canonical README for one immutable commit/ref.

CR-1 may establish only:

1. whether a canonical README is resolvable for the exact pinned repository state;
2. the canonical README repository-relative path returned by the resolver;
3. the canonical README Git/blob identity if returned by the resolver.

CR-1 must not enumerate repository or directory entries and must not use code search, filename search, globbing, or fallback README filename guesses.

Zero canonical README resolution fails closed.

Multiple or ambiguous canonical README resolution fails closed.

Preserve:

`CANONICAL README RESOLVED != README CONTENT READ AUTHORIZED`

`README IDENTITY != README CONTENT`

`README PATH != MANIFEST PATH`

`README IDENTITY != SOURCE IDENTIFIER`

### CR-2 — separately authorized bounded README content read

Only after CR-1 has independently established exactly one canonical README identity and that CR-1 result has been independently reviewed and promoted may a separate CR-2 task sheet be proposed.

CR-2 is a non-source documentary content read.

CR-2 requires:

- a separate task sheet;
- exact canonical README identity pinned by repository + immutable commit/ref + path + Git/blob identity;
- an explicit read budget of exactly one canonical README document;
- independent GPT L3 review before the read;
- no repository/path enumeration;
- no source-content read;
- no manifest-content read.

Preserve:

`README CONTENT READ != SOURCE CONTENT READ`

`README CONTENT READ != MANIFEST CONTENT READ`

`README CONTENT READ != SOURCE INSPECTION`

`README CONTENT READ != MANIFEST PROBE`

## 5. Exact documentary qualification rule after CR-2

A future CR-2 review may carry forward at most one exact repository-relative technical/config/manifest path only if it is explicitly written in the canonical README as an actual path used by the repository.

A qualifying path must NOT be:

- a placeholder;
- a pattern;
- a wildcard;
- an example unrelated to the repository;
- a command template;
- a generic conventional filename shown without repository-specific use;
- a path inferred from prose;
- a path inferred from Flutter/client/package/workspace terminology;
- a path copied from earlier BIB-03 hypothesis artifacts;
- an FD02 path or a path derived from protected-path information.

No ranking among multiple qualifying paths is permitted.

If CR-2 yields:

- exactly `0` qualifying actual paths: fail closed;
- exactly `1` qualifying actual path: at most one documentary path candidate may be carried forward to a later separate binding/ML-1 governance step;
- more than `1` qualifying actual path: fail closed, no ranking or selection.

Preserve:

`EXPLICIT README PATH != PATH EXISTS AT TARGET COMMIT`

`EXPLICIT README PATH != CANDIDATE ACCEPTED`

`EXPLICIT README PATH != BOUNDED BASIS INSTANCE ACCEPTED`

`EXPLICIT README PATH != SOURCE-TARGET BINDING`

`EXPLICIT README PATH != INSPECTION AUTHORITY`

`EXPLICIT README PATH != READ BUDGET`
