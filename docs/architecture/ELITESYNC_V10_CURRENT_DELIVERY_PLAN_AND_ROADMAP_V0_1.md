## 4. 最短依赖与尽早运行反馈

核心顺序：R18-R1 独立接受 → 必要 Connection 消费接口 → Messaging/Conversation → Home/Notification 所需活态摘要 → 同一可运行客户端主循环验收。

把“最小平台运行证明”放在 R18-R1 收口后的最早可授权位置，不等 M3/M4 全完。其前置仅是平台／源码／工具链授权充分，不是所有后端完工。若核心代码仍在审查，可由另一个获准且写集合独立的执行者处理；只有一个执行者时交错排程，不虚构并行折扣。

Connection HTTP 不是形式性硬前置：仅在客户端／下游实际消费需要时确定最小 transport，并与对应消费验证合包。不得自行添加 endpoint；也不得省略跨进程调用实际需要的传输。

最小运行 task 应一次覆盖：精确受限来源与平台 gate、允许的有界环境确认、安装／启动、一个稳定行为及回执；失败只定位该 lane，不“先做环境总审计，再写环境恢复计划，再审计划”。不可缺少的历史授权仍须核验，不以提速绕过。

## 5. 演示必须有可操作状态，而不仅是投影

Readiness/Match synthetic HTTP、Connection derived persistence 都不等于真实 source writers。可操作 synthetic 演示另需确定测试 actor、明确的状态驱动／写入夹具、可重放输入、同意序列与按环境声明的保存／恢复。它们须通过后续精确工程任务授权；本路线不发明生产 auth/session 或允许真实数据。

同一客户端的核心验收路径：准备状态 → 匹配机会 → 独立 Connection 同意 → 独立交流同意 → 测试消息读写 → 暂停／关闭／失效后正确限制 → 再进入应用按约定恢复。Block 的保护行为只在其已授权边界测试，不启动 Safety Operations；Report 不被解释为 Finding。未完成环节明确 unavailable，不能硬编码成功。

## 7. 后续时间花在哪里：计划分配，不是历史统计

以下分母为“完成单平台 synthetic MVP 的有效工程投入”，不含 Owner 等待、额度等待、机器空转、外部审批或未知环境停顿。它不是产品完成率、代码行占比或报告实测值。

| 活动类别（互斥） | 计划份额 | 具体内容 |
|---|---:|---|
| 新增功能与缺陷修复的产品代码 | 40% | 当前 correction、consent/messages、测试状态驱动、领域功能 |
| 当前 v10 资产适配／集成代码 | 20% | 现有 UI/provider/路由/契约与稳定接口衔接；也是写代码 |
| 测试编写、回归、设备联调与验收 | 20% | 负向用例、平台行为、状态恢复；含测试代码但不计入前两项 |
| 读源、必要继承核验与接口理解 | 8% | 仅本次消费的 v10 文件、固定契约／source manifest |
| 独立审查、必要任务／结果／状态文档 | 7% | 一次实质 review 和精确发布，不增形式性链 |
| 工具链／构建环境处理 | 5% | 有界离线恢复及必要环境问题，不是无限预算 |
| 合计 | 100% | 产品与适配代码 60%；加验证为 80% |

直接访问／继承旧 `EliteSync` 9.x 仓库的预算为 0%：它仍禁止访问，当前路线没有这种依赖。这不否定当前 v10 已存在的历史来源资产；其读取计入 8%，适配代码计入 20%，不重复计算。

每个任务实际构成会不同。若平台恢复持续占用投入，报告真实阻塞并修正预测，而不是为了凑 5% 跳过检查。无实际工时记录，不能声称已达到这些比例或已经提速若干倍。

## 8. 自底向上工作量假设：到可安装 synthetic MVP

以下为 task author 的初步估算，不是外部报告给出的数字，也不是历史吞吐推算。1 有效工程日按 6 小时投入（编码、读源、验证、审查等）作模型单位；没有证据证明当前团队实际每天有此容量。

| 交付块 | 低／高有效工程日 | 可复用资产／主要不确定性 |
|---|---:|---|
| R18-R1 修正、回归及独立接受 | 1–2 | 三 Phase-A blobs 原样复用；不重做 persistence |
| 最小平台安装／启动及稳定行为 | 2–5 | 已有客户端；工具链授权／本地环境未知 |
| Readiness/Match/Me/Onboarding 现有 UI 接口适配 | 4–7 | APP-T12 和已接受接口复用；实际接线证据待补 |
| synthetic actor／状态驱动／保存恢复契约及实现 | 2–5 | 不建立真实认证；投影不是 writer；需精确授权 |
| Messaging consent／读写／暂停关闭与客户端接入 | 5–10 | fail-closed UI 复用；核心后端和退出行为尚需闭合 |
| Home/Notification/Privacy 活态衔接 | 3–5 | 现有展示复用；系统投递范围单列 |
| 全主循环、离线／失效／重启回归及可安装包 | 3–6 | 目标平台证据与缺陷修复；不重复上列适配 |
| 总计 | 20–40 | 120–240 小时的假设模型，不含未知外部等待 |

这些是工作块，不是每块强制一张治理任务；相邻已确定行为可以合包。环境先行节省的是迟到反馈，不是在数学上自动减去一个月。连续完成两个至三个可比较交付包及最小平台证明后，用已有回执初步校准；样本小不输出统计分位数。

## 9. 日历窗口与失败条件

以 2026-09-21 为情景起点，不承诺后台推进。串行等效日历周 = 剩余有效工程日 / 每周实际有效工程日，再加“尚未计入的”关键路径等待；不能把同一等待重复计算。

|---|---|---|
| 最小平台证据检查点 | 目标 2026-09-28 至 2026-10-05 复核 | 优先收口当前 correction，再最早授权运行；检查点不是交付保证 |

先前聊天中的“12 月／2027 年 1 月”只是旧情景，不是三个月技术下限；也不能因本轮文档优化保证 10 月交付。上述更早窗口来自显式工作量／容量假设，并非测得的提速。
