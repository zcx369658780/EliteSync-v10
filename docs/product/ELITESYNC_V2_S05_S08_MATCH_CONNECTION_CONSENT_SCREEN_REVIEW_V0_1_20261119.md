## 1. S05 匹配准备：可补资料 ≠ 不可用外部依赖

| 检查项 | 顾问逐屏建议 |
|---|---|
| PURPOSE | 首眼知道“距离有资格参加真实匹配，还缺什么”，而非把整个匹配功能当作已经可用 |
| CURRENT_STATE | 将`Lifestyle 已确认完成数/5`、必要资料与具名用途、真实核验服务状态、当前报名授权分开；字段是否存在/核验是否可用必须是权威事实 |
| PRIMARY_ACTION | 只突出**当下本人能够合法完成的一项准备任务**；例如Lifestyle 2/5时“继续生活方式探索”。当所有用户可补项目已完，但核验供应商未接入时，首要呈现“真实核验暂不可用”，不得出现有效报名 |
| SECONDARY_ACTIONS | 去唯一有权字段编辑页、查看准备说明、返回首页、查看当前独立自动参与授权；不以自动参与替代本轮报名 |
| AUTHORITY | 当前账号+当前Lifestyle已确认进度、字段来源和用途、实人核验真实供应商状态及正式匹配资格 |
| RETURN_PATH | 补Lifestyle或必要字段确切成功后返回该Match准备任务并重读当前资格；退出返回合法一级入口 |
| RECOVERY | UNKNOWN先只读查状态；真实供应商未接入则显示外部依赖不可用；资料/授权失效不沿用旧进度；切号与Block重新验权 |

已获Owner确认的A67-R3要求**“用户可完成的缺项”和“供应商尚未接入”分别显示**。任何“认证通过”“立即报名”或真实候选时间/成功视图都不能是当前环境的真实功能说明。星盘、MBTI等可选工具不列为真实匹配硬门槛。

### S05-D1 本轮顾问建议（新的具体优先级，尚待Owner）
当存在多个可补项时，**仅强调当前最自然的一项可由本人完成的下一任务**（例如未完成的Lifestyle）；其它缺项以次级、可查看方式保留。无法完成的供应商核验不得与用户缺项排在同一个可点的“完成进度条”中。即使用户可补项全部完成，真实报名仍必须保持不可用并提供清楚安全返回，而不能设计虚假100%可报名。

该建议是信息层级与CTA默认优先级，不批准具体准备卡排序字段、进度百分比或自动申请权限。

## 2. S06 匹配准备→字段编辑→原任务

| 检查项 | 顾问逐屏建议 |
|---|---|
| PURPOSE | 补齐当前真实匹配准备所需且仍缺失/无效的一项资料或具名用途许可 |
| CURRENT_STATE | 权威来源的已知值、当前用途是否许可、用户尚未确认的编辑内容分开；当前城市≠出生地点、法定姓名≠展示昵称 |
| PRIMARY_ACTION | 编辑并保存当前必要字段；合法可复用数据直接预填，缺失许可单独请求具名同意 |
| SECONDARY_ACTIONS | 返回原任务、取消未保存内容、查看字段用途及修改影响 |
| AUTHORITY | 单一来源事实的有效版本、当前合法用途、账户与资格；不能用已存资料推导任意展示受众 |
| RETURN_PATH | 保存确切成功→回到先前Match准备任务，重新读取资格；若由Me自主进入则返回Me原位置 |
| RECOVERY | UNKNOWN先只读查真实版本，不能自动二次保存；失权/切号隐藏受保护输入与缓存；冲突由版本与权限规则处理 |

此路径已经在O04/O09得到Owner**概念认可**。新版本的页面内部表单数、字段映射表、是否需要单独保存授权、接口幂等事实仍OPEN。

## 3. S07 有效提案→Connection（只限未来具备完整前提的条件性场景）

| 检查项 | 顾问逐屏建议 |
|---|---|
| PURPOSE | 判断是否继续了解当前有权匹配提案；双方提案同意后**再分别决定**是否建立Connection |
| CURRENT_STATE | 当前提案是否有效及本人/对方分别是否同意；尚在等待另一方、被拒绝/撤回/过期时准确显示 |
| PRIMARY_ACTION | 视当前有效阶段提示“查看提案并决定”或“决定是否建立Connection”；不存在把两种同意合并的按钮 |
| SECONDARY_ACTIONS | 对应阶段拒绝、撤回、稍后、返回或阅读当前合法候选信息 |
| AUTHORITY | 每阶段的服务端当前业务事实/版本、双方分别的意愿及当前候选展示权；Block/受众/账号有效性 |
| RETURN_PATH | 本人有权决定确切提交成功后仍停留在当前连贯任务上下文，更新为真实下一状态或等待对方；退出回当前匹配历史/安全位置 |
| RECOVERY | 一方未同意→等待；拒绝、撤销、过期、Block→停止推进；UNKNOWN先只读查询，不自动重放同意；旧通知只重验后导航 |

**约束：** A4七类状态不意味着七个强制页面，不能用“一个连续界面”替代两种真实独立决定。Relationship也不由Connection自动建立。

## 4. S08 双方Connection有效→双方Messaging Consent→有权聊天（条件性场景）

| 检查项 | 顾问逐屏建议 |
|---|---|
| PURPOSE | 当前阶段询问“双方是否愿意允许私聊”，而不是因为已经建立Connection就开放聊天 |
| CURRENT_STATE | 必须能正确区分本人许可/对方许可仍待/双方均有效/任何一方撤回/失效；如果双方未全部有效则不可读写会话 |
| PRIMARY_ACTION | 本人尚未同意时给出明确的消息许可决定；双方有效后才突出“进入聊天”（进入不代表自动发送消息） |
| SECONDARY_ACTIONS | 拒绝、撤回、稍后、返回上一合法业务页，权限说明 |
| AUTHORITY | 当前账号、双方Connection与Messaging Consent的独立有效事实、版本、Block和会话受众 |
| RETURN_PATH | 本人许可确切保存后，若对方尚未同意留在等待阶段；双方均有效才能进入有权会话；返回按当前任务上下文重验 |
| RECOVERY | 任一方撤回/过期→停止读写并隐藏失权会话媒体；UNKNOWN不自动重复许可；旧深链、账号切换重新核查 |

这一页将“消息许可”与“Conversation首次主动发送”分开；不将好友、Buddy或作品互动变成消息许可。

### S07/S08-D2 本轮顾问建议（具体连续导航，尚待Owner）
在真实且合法的匹配链可运行之后，使用**同一任务上下文中按阶段变更的单一主操作**，在提案决定、Connection和Messaging Consent各自完成独立权威提交后自动更新下一步指引；**不要求用户每阶段返回四入口再重新寻找入口**。但每个阶段的同意/拒绝/撤回需独立可见、独立本人提交，当前等待另一方时只显示等待/撤回/退出，不自动提前显示下一阶段授权按钮。

该建议仅确定**导航及文案的低操作成本方向**；不冻结屏数、按钮文案、过期倒计时、后台状态机或当前环境的可执行真实性。

## 5. 跨四屏一致性与禁止混淆

| 关键情况 | 正确概念表现 | 不能发生 |
|---|---|---|
| Lifestyle 2/5 + 核验未接入 | 继续可补Lifestyle；单列“实人核验暂不可用” | 显示“完成最后一步就能报名” |
| Lifestyle已补齐、其它必要资料已齐，但核验未接入 | 清楚的外部不可用状态与返回；真实报名不可点 | 虚构报名成功/已有候选 |
| 补必要资料超时UNKNOWN | 停留“结果尚未确认”，先查服务端真结果 | 自动重发、假保存 |
| 未来匹配提案本人接受，对方未接受 | 等待对方独立决定，必要撤回可用 | 自动显示已建立Connection |
| 未来双方Connection成立，仅本人同意消息许可 | 等待对方许可，不显示可读写聊天 | 自动创建可读Conversation |
| 未来消息许可一方撤回/Block | 立即失权脱敏/受保护读写门禁关闭 | 保留旧私聊正文为截图 |
| 旧通知深链进入过期提案 | 只返回当前合法业务或安全历史 | 用通知一键接受过期提案 |

## 6. QA范围与状态（仅定义，全部NOT_RUN）

- 身份核验服务未接入时APP禁用真实报名；不同账号、模拟数据不得假造有权链；
- 双方各自提案接受/拒绝/撤回、独立Connection/Consent，前一步不代替下一步；
- 从Match补必要字段成功/失败/UNKNOWN回流；旧账号迟到请求与跨设备权限失效；
- 聊天读写/媒体/通知深链的当前许可、Block与版本门禁；
- 用户首眼理解、额外导航N、必要决定D、重复输入I、后台A及等待W，含无障碍/系统Back/减少动效。

本稿**没有**进行上述真实APP/API/DB/Web、设备、模拟器或资格测试；不能把未来验收情景写成PASS。

## 7. 本轮最小Owner审阅建议

建议只审两个具名细化点：
- **S05-D1（顾问建议）**：在匹配准备页将“当下可由本人完成的一项任务”作为突出主操作，并将真实核验供应商“尚未接入”清晰列为**不可由本人补齐的外部依赖**；任何情况下不得假显示当前真实报名入口可用。其它准备项可次级展开，不隐藏必要的授权和拒绝。
- **S07/S08-D2（顾问建议）**：在未来各真实资格齐备时，将“提案决定→Connection→Messaging Consent”的导航组织成**同一任务上下文连续引导**，但每阶段必须双方各自独立明确决定与当前服务端确认；等待/拒绝/过期/撤销时停留该阶段并安全返回，不提前显示下一许可。

若Owner接受，仅上面两个**增量的UI层级与导航建议**成为概念认可；S05–S08中未来供应商接入、具体实施及逐像素布局依然未获批准。
