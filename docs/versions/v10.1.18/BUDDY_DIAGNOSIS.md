# Buddy 独立诊断

本轮使用新建 v18 隔离 MariaDB、虚构账号与现有 Buddy HTTP 接口。Owner 在 v17 实机上遇到“可进入但无法匹配”的确切原因仍为 UNKNOWN，该次手机请求、筛选与候选池未留存。

## 实际链路

`/buddy-v1013` 进入 BuddyPage，读取 `/buddy`。发现页读取 `/buddy/discovery`，活动创建、开放、发布与申请分别调用既有接口。BuddyService 与恋爱匹配使用各自的业务合同。

发现列表按活动类型和城市精确筛选。默认条件为线上、吃饭。活动需处于 OPEN，经过本人明确发布，发布与偏好版本有效，开始时间尚未到达，发布者和查看者账号、Buddy 许可及双方访问条件有效。创建 DRAFT 或仅开放活动后，发现列表仍可为空。

## 隔离 HTTP 与数据库验证

| 条件 | 本轮实际结果 |
|---|---|
| Buddy 许可尚未开启 | HTTP 403，提示先开启 |
| 开启许可，尚无公开活动 | 空列表 |
| 学习活动 OPEN，尚未发布 | 学习发现列表为空 |
| 明确发布学习活动，搜索吃饭 | 空列表 |
| 同一已发布活动，搜索学习 | 返回一项 |
| 虚构申请者明确申请 | REQUESTED，等待活动发起者回应 |
| 发起者明确拒绝 | 按既有动作结束该次申请 |

另留存一项虚构学习活动供最终候选的真实 APP 发现流程复核。HTTP 最终集中回执记录16项具名检查，包含主体隔离和候选筛选。Buddy 与 B2 定向 PHP 共34项、438个断言通过，使用测试进程中的 SQLite 内存库。上述 HTTP 行为另由新 MariaDB 持久化验证。

本版发现页将城市、类型与空结果提示改为可执行的产品语言。现有入口、参数和接口能完成上述流程，本轮没有证据支持调整 Buddy 算法或候选策略。Owner 原手机问题的原因保留 UNKNOWN。

## 测试环境恢复

新隔离环境初次注册在写日志阶段返回500，账号行已提交。保留失败后修复新 storage 卷属主，并通过该虚构账号正常登录恢复。随后补齐当前匹配资料接口要求的六项 nullable 字段，以及新实例的精确数据库资格绑定。API/WS 在本版新容器恢复。原开发库、v17 库及历史逐表 UNKNOWN 保留。

消息准备使用一份预生成的受控匹配结果和虚构双方显式接受、连接、消息许可。补齐了该受控结果对应的两条每用户轮次投影。整个准备过程未运行管理员匹配轮次。服务、业务 API 与数据库结构的产品源码沿父版本实现。

实际 APP 验证和截图见 [冷启动与隔离回执](COLD_START_ACCOUNT_ISOLATION_RECEIPT.json)。
