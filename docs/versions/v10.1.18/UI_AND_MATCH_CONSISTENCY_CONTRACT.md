# v10.1.18 产品与交互合同

## 1. 目标

本版是B3后的UI表达与交互一致性收口。以Owner在REDMI K80 Ultra / Android 16上的有限观察为直接输入，解决开发式文案、一级入口命名、选中态文字可读性、自动化入口不易发现的问题，并补充Buddy诊断及冷启动/账号隔离验证。

不重新设计整体美术方向，不新增社交功能，不做B4。

## 2. 用户语言合同

### 2.1 原则
- 用户文案应像成熟消费级产品，不像接口日志、程序注释、开发者诊断或免责模板；
- 简短、自然、具体，优先描述用户当前能理解的事实与下一步；
- 不把内部状态码、字段名、技术原因直接显示给普通用户；
- 不用过度解释来掩盖状态不确定；
- 错误/未知状态应诚实、可恢复、避免将未知写成成功或失败。

### 2.2 必查文案
至少审查首页状态卡、轮次状态、主要按钮、生活方式探索、自动化状态、匹配说明、空状态、错误状态、权限说明、Buddy空池/无结果提示。

对“账号可用”“本轮暂无候选，不代表被拒绝”等文案提出逐条替换方案。最终文案应表达当前可确认的事实，不强制沿用本合同示例措辞。

## 3. 一级入口「进展」→「匹配」

- 将底部一级入口和对应页面标题从「进展」调整为「匹配」；
- 默认保留Home、匹配、消息、我的四个底部入口，不新增第五个；
- 页面围绕当前匹配状态、当前轮次、候选/提案、历史匹配结果和用户需要作出的决定组织；
- 不再把恋爱关系的主观体验包装为APP能够判定的“关系进度”；
- 只展示服务端已有且当前用户有权读取的业务事实；
- Match、Connection、Messaging Consent、Conversation、Relationship仍然分别呈现；
- 旧`/progress`路径、route name、通知跳转、深链和历史入口保持兼容或安全重定向；外部链接不得失效；
- 不改变匹配资格、候选排序、匹配算法、提案决策、Connection/Consent状态机。

## 4. 按钮与选项统一配色

建立单一主题/组件状态映射，覆盖：
- primary / secondary / tertiary；
- default / pressed / selected / disabled；
- destructive / warning（仅在现有语义需要时）。

要求：
1. 文字与背景在每种状态下保持可读，选中态不能出现“整个按钮高亮导致文字看不清”；
2. 使用项目当前色板和低刺激方向，不擅自引入高饱和霓虹；
3. 避免各页面自行硬编码不同按钮颜色；
4. 复用共享组件/Theme token，必要时只迁移本版涉及页面；
5. 测试浅色/深色（若现有支持）、正常/放大字体和选中/禁用状态；
6. 文本对比参考WCAG AA：普通文字至少4.5:1，大字至少3:1；非文本控件边界和状态提示至少3:1。若项目有既定更严格标准则遵循既定标准；
7. 状态不仅靠颜色区分，还要有文字/图标/形状等可理解提示。

## 5. 自动化入口可发现性

- 用户本轮无法找到自动化入口，必须解决；
- 在「匹配」页面提供一个可见、易懂的持续参与/自动化摘要或入口；
- 在「我的」中提供清晰的设置入口；
- 所有入口必须指向B2唯一规范的`UserStatePage`/授权控制页面，不复制控制状态或开关；
- 使用普通产品语言解释“持续参与”具体会做什么、不会做什么；
- 默认关闭和明确授权保持不变；
- pause/resume/revoke和权限revision合同不变；
- 不新增频繁推送、打卡或提醒。

## 6. 说明与免责声明收敛

- 一般性持续说明、隐私用途说明和较长免责声明集中在「我的→权限/说明」；
- 首次参与匹配时提供必要的一次性简短说明；若后端/本地已有已确认版本记录，复用现有合同，不重复弹出；
- 版本变化需要重新说明时，只针对变化部分；
- 不删除法定/必要信息，不将隐私分享、身份、匹配接受、消息同意、Connection、Relationship和不可逆动作的明确确认移出上下文；
- 不把“少弹窗”解释成静默授权。

## 7. Buddy独立诊断边界

诊断至少区分：
- UI入口/路由问题；
- 账号/用户资料状态；
- Buddy专属资格/筛选条件；
- 请求参数、API响应和错误码；
- 候选池为空、候选已耗尽或测试数据不足；
- 服务端算法/排序/候选生成问题；
- 当前部署配置或后台任务问题。

使用虚构账号与隔离数据。不得把恋爱匹配的资格或算法直接套用到Buddy。若确认是UI/路由/配置/接口接线缺陷，可在本版修复并定向验证。若根因属于Buddy算法、策略、权重、候选池产品规则或需要新业务状态，先形成独立诊断和方案，标记UNKNOWN/OWNER_DECISION_REQUIRED，不擅自大改。

## 8. 冷启动与账号隔离合同

Owner本轮只观察到新账号未显示旧账号消息，完整切号和冷启动仍未验证。

在同一模拟器安装、同一applicationId下，至少完成：
1. A登录，加载Home状态、消息列表、通知和一个账号私有页面；
2. A正常登出；
3. B登录，检查Home/Progress/Match、消息、通知、缓存、草稿均不包含A内容；
4. 强制停止APP进程并冷启动，B仍只看到B自己的内容；
5. B登出并重新登录A，A内容按原授权恢复，B内容不泄漏；
6. 在网络可用和短暂断网/恢复场景检查账号切换不会复用旧账号离线缓存；
7. 记录每一步的账号ID/虚构标识、token变化、缓存命名空间、HTTP主体、数据库主体和可见内容摘要（不记录秘密token）。

冷启动定义为进程被终止后重新启动，不以普通页面返回或热重载替代。不得删除生产数据或清理Owner手机。测试账号和隔离库必须可销毁、可重建。

## 9. 版本与范围边界

- 候选建议`10.1.18-dev / 1011801`，必须核对versionCode、applicationId、签名和历史候选占用；不得覆盖1011703或1011601。
- 不操作Owner手机；交付新APK和更新的Owner验收表。
- 不改匹配算法/候选排序/资格权威服务/关系状态机。
- 不做B4运行时AI，不接身份、征信、芝麻信用、蚂蚁积分、Push、支付或新供应商。
- 不合main、不正式发布、不开展真实内测/运营。
