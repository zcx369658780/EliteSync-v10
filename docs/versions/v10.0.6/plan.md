## 2. 同一版本的实现范围

### A. 开发数据库与真实资料链

专用配置不复制原根 `.env`、生产密钥或远端服务目标。优先依现有迁移建立本版独立MariaDB库，核users、sessions、personal_access_tokens及相关资料列；必要迁移兼容修复和seed属于本版。使用持久volume，不以SQLite内存或运行内状态代替最终数据库。

只创建三个明确标为虚构的本版账号：管理员、待禁用普通用户、正常对照用户。账号密码/令牌仅保留适当本地配置，不提交凭据或将客户端自报的role/realname字段当身份依据；seed只创建/管理本版记录，不能误改同号既有用户。管理员名单显式配置。

APP复用原登录、编辑资料、城市字段和现有接口，增加独立“保存城市”动作，保留完整资料保存/重算路径。城市保存不触发八字、紫微、西占或渲染服务；不把已有完整功能删除后声称恢复成功。保存失败、401/403、失效token必须表现为失败或会话失效，不能通过缓存回退返回成功；缓存可保留历史显示，但必须可识别且不伪装最新服务端确认。

### B. 可操作的Blade管理端及一致业务规则

在现有Laravel中实现独立 `/admin` Web入口：登录、退出、用户列表/必要信息、禁用表单及成功/失败反馈；复用User模型及共享管理业务服务，不新增React、Flutter Web或第二套业务数据库。管理员登录与角色授权分别验证。

Web和本版涉及的管理API统一要求有效且未禁用的服务端账号、`role=admin`和明确管理员名单。空名单拒绝；普通用户即使号码在名单里也拒绝；不得由local环境、默认开发捷径或请求中自报role绕过检查。允许修正共享管理员鉴权中的相关捷径，不以此执行本版外的匹配操作。Web使用CSRF、登录后session regenerate、退出session失效；负向验收包含普通用户携带有效CSRF的请求，而不是只有缺CSRF被拒。

将现有禁用逻辑抽取为API和Web共享动作：事务中更新现有禁用/关联标记、撤销该用户token并处理其持久session；本版账户/资料/管理访问验证有效账号状态。`refresh`不得给禁用账号发新token，旧token和旧session不能恢复业务访问。避免“先检查再错误续签”绕回；实现策略和必要锁/状态检查由Codex在模块内决定，不要求重设计全仓鉴权。

成功禁用后APP对同一账号的后续资料读写及重新登录被拒，正常对照用户仍能操作；Web退出后原管理员session不能继续管理。保留独立阶段同意与BE-12消息保护；本版不增加恢复用户/批量封禁/完整运营系统作为额外目标。
