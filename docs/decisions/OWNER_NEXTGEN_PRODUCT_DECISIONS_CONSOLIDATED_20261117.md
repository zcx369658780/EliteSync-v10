## 1. 产品定位与全局体验

### 1.1 整体原则 — OWNER_CONFIRMED

1. EliteSync是关系决策辅助系统，不是替用户作出关系决定的判官或追求最大停留时长的内容平台。
2. 优先完成低操作成本、图像主导/短文案、按需收集资料；先体验产品价值，用户主动匹配时再补充必要字段。
3. 底部四个一级入口继续为`首页 / 匹配 / 消息 / 我的`，整体调整这些入口的任务归属而非任意增加一级入口。
4. 视觉方向为**构成主义为主的二次元卡通画风**：几何色块、明确构成、风格化二次元人物/场景；保留水中倒影/画面幻化的转场构想作为可进一步讨论的**非写实动效概念**，不将其等同于写实摄影、玻璃拟态或真实水面反光。
5. 讨论用视觉稿优先低分辨率设定图、低保真方向稿；字体、配色、选中态遮字、阅读密度及转场实际实现方案待正式设计时统一处理。

### 1.2 永久业务边界 — EXISTING_BASELINE

- `Match ≠ Connection ≠ Messaging Consent ≠ Conversation ≠ Relationship`；任何一个状态都不能自动推出下一个。
- Buddy活动/搭子申请独立于恋爱匹配，不自动建立好友、消息许可或Relationship。
- 访客访问、内容受众、评论许可、好友关系、Block和通知回流必须由服务端当前权限决定。
- 资料存在不代表拥有任意用途或公开权限；计算结果不等于客观人格/关系判断；私聊、敏感信息不自动用于内容推荐或匹配。
- 真实身份供应商、真实Push、B4运行时AI和阶段C仍未授权。

## 2. Home：首页与内容社交

### 2.1 信息架构 — OWNER_CONFIRMED

- 首页以**平台精选 + 好友动态**为主要内容。
- 首页内部两个频道：`精选`（默认）与`好友`。
- `精选`频道包括明确区分的**官方精选/官方专题**和**用户公开作品**独立区域；公开作品不另设第五个一级入口。
- `好友`频道显示本人及当前有效双向好友可见的动态，不自动提升为公开内容。
- 首页保留低干扰的本人匹配入口，但不能恢复为多行状态面板或泄露他人状态。

### 2.2 三种内容来源与访问 — OWNER_CONFIRMED

| 来源 | 访问者 | 互动规则 |
| --- | --- | --- |
| 平台官方精选/专题 `PUBLIC_EDITORIAL` | 访客可读正文，登录用户亦可读 | 普通精选对登录用户开放点赞、收藏；指定官方专题按类型开放评论 |
| 用户站内公开作品 `PUBLIC_AUTHENTICATED` | **仅账号有效的已登录用户** | 作者逐条设定谁能评论；站内公开不等于访客可读 |
| 好友动态 `FRIENDS`、仅自己 `SELF` | 本人及当前具有效访问权限的双向好友 / 仅本人 | 保留当前权限、Block及互动合同 |

- 未登录访客在APP任何地方**不可提交评论、留言、点赞、收藏、举报、站内反馈或其他用户互动**；只能阅读允许访客阅读的官方精选/专题正文。登录/注册与必要账号恢复入口不属于匿名互动。
- 未登录访客不得看到用户公开作品、好友动态、私聊、私人身份或匹配资料；直接URL、深链、图片/视频媒体地址、通知和缓存均不能绕过服务端权限。
- 登录不等于获得匹配资格，也不代表能访问其他用户的私人资料。

### 2.3 发布及评论 — OWNER_CONFIRMED

- 用户新建作品**默认仅好友可见**。可主动选择`SELF`、`FRIENDS`、`PUBLIC_AUTHENTICATED`，切换受众必须体现实际权限变化。
- 用户作品评论权限可选：`ALL_ELIGIBLE`（当前有权读取且未被Block的登录用户）、`FRIENDS_ONLY`或`OFF`。
- 评论有效条件至少包含：登录与账号有效 + 当前作品可见 + 评论策略允许 + 无Block。
- 官方专题采用**B类问题引导讨论**：官方账号提出具体问题、按内容类型开放评论；普通官方精选默认不是开放评论区。
- 公开用户作品不自动成为平台编辑作品，不自动建立全局公开个人Profile、好友、Connection、Messaging Consent或私聊。
- 平台转为编辑推荐/转载用户作品时，原有私密受众不能无授权升级为公开；审核、转载授权等详细合同仍为OPEN。

### 2.4 当前工程差异

现有1011804中用户动态后端仅有`SELF/FRIENDS`，用户登录后可见的站内公开作品、官方公开内容域及作者评论模式尚未按本文件交付。该文件是目标设计，不能作为新功能已存在的证明。

## 3. Matching：匹配与关系旅程

### 3.1 渐进式准入 — OWNER_CONFIRMED

- 注册后引导五场景Lifestyle探索，但注册阶段**可跳过**；普通内容与可用社交功能不因此全部锁定。
- 用户主动选择参与真实匹配前，**必须完成Lifestyle**。
- **真实实人认证通过**是正式参与真实匹配前的必要条件；当前真实供应商尚未接入，不能用测试凭据、运营审核或自我声明代替，不得把占位按钮显示为已核验。
- 还需遵守其他必要匹配资料/资格合同，并由用户主动明确报名或另行授予自动参与权限。
- MBTI与五场景Lifestyle是独立功能，MBTI可选，不替代Lifestyle。

### 3.2 自动参与 — OWNER_CONFIRMED

- 普通报名只作用于当前明确选择的轮次；不默认开启持续自动参与。
- 自动参与默认关闭，需独立明确授权；暂停、恢复、撤销分开控制。
- 自动报名不代表自动接受候选、建立Connection、给予Messaging Consent、开放聊天或确立Relationship。
- 手动报名不会因自动授权暂停/撤销而被无条件取消；B2的已有授权生命周期继续有效。

### 3.3 星盘与资料 — OWNER_CONFIRMED

- 具备足够且可用的出生资料、相应用途授权时，星盘可以自动生成；**星盘不作为匹配硬门槛**。
- 缺出生时间/地点、计算失败、核验未完成不应因为星盘原因阻断其他资格已满足的匹配；不能虚构时间/地点或计算成功。
- 法定姓名、生日、出生时间、出生地点、当前城市、展示昵称分清含义、来源和使用目的。
- 已提供资料在有效授权下可复用/预填；只请求缺失且当前目的必要的字段，取消重复填写。
- 实名供应商的实际字段、范围及失败恢复等仍为OPEN。

### 3.4 页面组织候选 — ADVISOR_PROPOSAL

将匹配首页组织为：`匹配准备 → 参与方式 → 本轮匹配 → 连接与关系 → 匹配历史`。只突出当前需要用户作出的下一步和状态；具体模块数、顺序和表现尚未由Owner逐项冻结。

## 4. Me：「我的」页面

### 4.1 顶部和导航归属 — OWNER_CONFIRMED

- 「我的」顶部以**个人资料卡**为主要内容，表现头像、昵称和个人形象预览，不以复杂业务状态看板取代它。
- **MBTI与西方占星、八字、紫微等统一进入「自我探索」中心**，在内部区分测评与不同计算工具；工具仍保留各自输入、结果、历史及核验状态。
- **好友与Buddy统一归入「社交与内容」的导航分组**，内部保持好友关系、Buddy活动与申请等独立业务/权限，不混同。
- 用户作品、草稿、收藏、受众和评论管理需要在「我的」有便于发现的入口；具体卡片分组与细节属于建议。
- 个人资料管理应减少重复填写、保留权限用途区分。

### 4.2 双形象系统 — OWNER_CONFIRMED

- 基础形象提供**主头像与主昵称**，社交形象和匹配形象默认复用它们。
- 社交形象、匹配形象可以分别修改头像和昵称（独立覆盖），且**展示权限独立**。
- 修改主头像、主昵称后，使用默认形象的**本人个人预览自动更新**；已经单独覆盖的字段不被覆盖。
- **对外匹配候选展示仍须遵守原有受众、有效发布版本及必要发布确认**。本人预览更新不等于自动向过去/现有候选公开新的展示版本。
- 社交形象不意味着对所有账号公开法定姓名或私密身份；匹配形象也不意味着创建公开候选目录。

### 4.3 结构候选 — ADVISOR_PROPOSAL

页面呈现建议：
1. 顶部个人资料卡与形象编辑/预览；
2. 个人资料：私密身份、出生资料、社交形象、匹配展示；
3. 我的偏好：Lifestyle、关系目标与匹配偏好；
4. 自我探索：MBTI、星盘、八字、紫微及历史结果；
5. 社交与内容：我的作品/草稿/收藏、好友及Buddy；
6. 隐私与授权：展示受众、数据用途、持续参与授权、Block；
7. 设置与账号安全：通知设置、外观、设备和账号安全。

这套分组本身尚未被Owner逐项批准，不能把`ADVISOR_PROPOSAL`误记为已批准的页面设计。

### 4.4 数据来源与权限 — 设计原则/待定实施合同

- 减少重复输入和默认形象副本；将事实数据来源、用途授权、受众权限和已发布快照分开。
- Personal Data Hub是顾问提出的统一来源概念，**并不意味着Owner已批准具体数据库schema、服务分层或新建表**。
- 已有基础/匹配/展示/出生资料仍存在各自有效版本及业务合同；未来先做映射，再决定是否需要增量后端。
- 修正原始资料后，派生计算结果的失效、更新及撤回规则待细化；不得自动改变已公开内容或匹配关系决定。

## 5. Messages：「消息」页面

### 5.1 页面信息架构 — OWNER_CONFIRMED

- 顶部使用`聊天 / 通知`**双频道**，默认进入`聊天`。
- 聊天未读与站内通知未读**独立计数**，不可将同一通知等同于会话消息，也不可互相清零。
- 通知频道按**待处理事项优先，普通通知按时间排列**组织。

### 5.2 排序解释及限制 — ADVISOR_PROPOSAL / EXISTING_BASELINE

- 待处理应该基于**当前服务端有效、确实需要用户亲自决策**的业务事项，如当前有效匹配提案、好友请求、Buddy创建人待处理申请。
- 待处理层下的普通通知按发生时间倒序；待处理内部的具体排序、分组与到期显示规则仍需细化。
- 已读与待处理不是同一状态：已读仍可能待决，未读也可能已失效。失效后不能仍提示可执行原操作。
- 不以通知卡片点击替用户执行高影响决定；通知是受控入口，需进入当前合法业务页再本人确认。
- 点击旧通知/深链时，目标重新核对当前账户、受众、Block、Connection/Consent、内容状态及有效业务版本。
- 聊天阅读确认与通知标读各自运行；打开频道不应默认为全部已读是顾问建议，需最终界面合同确认。
- 单张通知卡只突出一个下一步操作、其他选项放次级菜单是顾问建议。
- 真实Push尚未接入，不把站内通知可读等同于设备Push已实现。

### 5.3 聊天/关系边界 — EXISTING_BASELINE

- 会话参与者、Connection、Messaging Consent和当前权限必须通过服务端事实核验。
- 社区作品评论、点赞、好友关系、Buddy申请或一次匹配接受均不能自行开放新私聊。
- 聊天文本/媒体的访问权限、账号切换与缓存隔离不能因新UI被放松；未授权内容不得从旧客户端缓存泄漏。
- 系统通知不得在锁屏中默认暴露候选人身份、私聊正文、精确身份/关系信息。

## 6. 跨一级入口整合 — 方向确认与候选方案

### 6.1 已确定的整体方向 — OWNER_CONFIRMED

Owner已经明确同意继续设计**「注册到聊天」完整用户旅程**，并以完整旅程反推跨入口信息架构，而不是继续向页面堆叠按钮。整体目标是减少重复输入、无意义确认和页面查找，同时保留真正必要的授权及关系决定。

### 6.2 单一业务归属建议 — ADVISOR_PROPOSAL

| 用户任务 | 建议主归属 | 从其他入口的捷径 |
| --- | --- | --- |
| 官方精选、公开作品、好友动态及内容互动 | 首页 | Me中的作品管理只负责作者管理 |
| 匹配准备、资格、报名、候选决定、Connection和Relationship | 匹配 | 首页小状态入口、通知回流 |
| 有效Conversation、会话管理与站内业务通知 | 消息 | 匹配连接成功后的聊天入口 |
| 基础资料、形象、工具、作品、好友、Buddy、用途与权限设置 | 我的 | 匹配准备可直达缺失资料字段 |
| 自动化持续参与权限 | 已有B2唯一授权控制页 | 匹配与我的均可跳转，不建立第二套开关 |
| 用户作品的创作入口 | 首页发布按钮 | 我的作品可管理、恢复草稿 |

具体路由、返回栈、页面主次分区尚未由Owner最终冻结。

- 老架构中的Home/Discover定义、用户受众与发布限制需要在未来V2迁移合同中显式整理，保留历史资料。

7. Me五大分组具体卡片位置、头像变更后的对外展示版本发布细节。
8. 通知待处理内部排序、已读时机、通知分组/静默、内容失效处理等细节。

10. 全局视觉设计稿、字体/颜色、转场动效及减少动态效果替代方案。
11. 公开作品是否需要活动/推荐系统、算法排序细节，必须与不做参与度最大化保持一致。
